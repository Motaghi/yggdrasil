# Yggdrasil v1.0.0

Version 1.0.0 is the first release of Yggdrasil. It has the conductor, approvals, the files and Linear trackers, and headless agent sessions on Claude Code, with Codex for the project reviewer and T3 Code as an optional launcher for Claude Code sessions. Projects on a folder of documents (`vault-docs`) are a preview. Its guards catch accidents; they don't contain a hostile agent. Read [Security](../security.md) before you run it on anything that matters.

## How it was proven

The release was proven by one end-to-end run. Yggdrasil took a small real project from its brief to main with no help, on the Linear tracker and a git repository, starting from fresh state on the released code:

- 25 agent sessions were started, and every start was confirmed.
- No launch was held, no session was started by hand, the main session sent no messages to the agents, and nothing needed repair.
- Every work package review ran on Codex and was recorded.
- Both work packages were accepted by the senior user and merged, and the project was closed.

The main session acted only for the user's three approvals: the project plan, the phase end and the merge into main.

Every change was reviewed by a Codex reviewer. On the release code, 1711 unit tests passed with none failing. The A11 acceptance suite failed only the 15 known rows planned for v1.1 (see below), the A11.1 suite passed 138 of 138, and the A7 suites passed. The published tree, which ships with three features switched off, was tested too: 1729 unit tests passed (the count includes tests added for the pre-publication fixes), A11.1 and the A7 rest suite passed, and A11 failed 26 rows by design, the 15 known rows plus 11 rows for the switched-off dashboard server. Three timing-sensitive tests that failed under heavy machine load each passed 3 times out of 3 when run alone.

## What changed during the release pilots

Each pilot run found one gap. The gap was fixed, reviewed, tested, and the run was repeated.

- **Launches.** A launch held before its agent started can be released, and `ygg status` no longer shows it as running. On Linear, launches no longer fail when Linear moves a document's version stamp after a write. The supervisor never starts an agent twice, and when it stops a launch it gives the reason in one clear line.
- **Reviews.** A reviewer is told the real path of its verdict file. A work package sent back keeps its open findings in the team lead's and the project manager's prompts across sessions. A senior user is told to test its work package now.
- **Planning.** The project plan template names `agent_commands`. Once you approve the plan, the project manager is told planning is done, so it no longer rewrites an approved plan in a loop. The project manager knows acceptance comes after review, and doesn't promise test runs it can't make.
- **Lanes.** In a git project, each lane carries one work package at a time, and that package is merged into integration before the next one is authorised. So a review sees only its own package.
- **Pushes.** A team lead pushes only when the repository has a remote and the brief allows it.
- **Blockers.** Every role reports a blocker through `ygg`, by its own route, never only in its final output. Team leads and workers check behaviour through a test and the approved test command.
- **Permissions on Linear.** Agents see your permissions agreement, so a false "not agreed" status no longer stalls a project.

## Setup notes

- **One Linear team per Yggdrasil installation.** The team's journal records one installation's safety folder, so a second installation (another state folder) on the same team refuses every launch with `safety folder ... missing or unreadable`. See [Trackers](../trackers.md#one-linear-team-per-installation).
- **Codex through a proxy or another provider.** If your Codex config has a provider that reads its API key from an environment variable (`env_key`), list that variable under `agent_env_passthrough` in your config. Headless agent sessions get an allowlisted environment, so the variable is dropped otherwise, and Codex reviewers fail at start. See [Configuration](../configuration.md#agent-environment).
- **Briefs that ask to match another tool's output.** The same tool can answer differently on another machine or locale; macOS and GNU `wc`, for example, treat a no-break space differently. Say in the brief which machine or locale counts.

## Limits of this release

- **Document folders are a preview.** A `vault-docs` programme works, but its work packages get no automatic per-package review: `ygg wp ready` is refused for them, and the team lead finishes a package with `ygg wp complete`. `ygg programme create` says so when you create one. Project reviewers are added only for git projects.
- **Codex runs the project reviewer only.** A project manager, team lead, worker or senior user on a GPT-family model is refused with "Codex builds come in v1.1", so a Codex-only setup (`launcher_cli: codex`) doesn't work yet.
- **One repository per git project.** A project plan that names more than one repository is refused at approval.
- **Switched off in this release.** These parts are in the code but off in the shipped build, because their acceptance tests don't pass yet:
  - `ygg dashboard serve`, which would serve the dashboard page on 127.0.0.1, is refused as not in this release. The dashboard file itself is still written.
  - The longer confirmation window for slow agent starts. A start gets only the fixed window, `launch_confirm_seconds` plus 10 seconds. A start that isn't confirmed by then shows as held, and nothing restarts or signals it until you check it.
  - Sending urgent messages straight into a running T3 thread. They go to the node's inbox, like other messages.
- **The 15 known failing acceptance rows** are behind these limits: the confirmation window (4 rows), sending into T3 threads (2), the dashboard server's network check (1, which needs a machine with a non-loopback address), and the commit guards and prompt for Codex team leads (8), which v1.0 refuses anyway. They are planned for v1.1. In the published tree 11 more rows fail, because they test `ygg dashboard serve`, which the shipped switches turn off; see [Contributing](../contributing.md#rows-that-fail-by-design-in-v100).

## Known defects, planned for v1.1

These are faults in behaviour this release supports, and tests still to add.

- **Codex reviewers.** A Codex reviewer sometimes writes its verdict in its own format. The automatic retry recovered it in the release run. The plan is to state the format more firmly and to read near-miss verdicts more tolerantly.
- **More tests.** An end-to-end Linear regression test with separate cache and user folders, and one for open findings across a real relaunch.
- **Project manager and plan.** Nothing in the code stops an approved project that is under way from being marked as having a plan ready for approval again; today only the prompt prevents it. The fix must keep a way to replan. The project manager should also be allowed to run the approved test commands.
- **Senior users.** A senior user's ruling has no agent route into the record. It needs the main session.
- **Commands and status.** The refusal "send without --from" is misleading when only `--kind` is missing. The blocker line in `ygg status` can be out of date. Once, after a decision was answered, the next launch came 17 minutes later; this is not explained yet.
- **Testing race.** A project manager reopening a work package can leave a senior user's testing details out of date before its session starts. Acceptance still refuses work packages that aren't ready.
- **T3 launcher.** Starting agents in T3 Code is experimental in this release. Besides the part switched off above, its known gaps are listed in [Security](../security.md#known-gaps).
